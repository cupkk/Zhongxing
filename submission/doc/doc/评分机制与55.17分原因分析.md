# 官方评分机制与 55.17 分原因分析

## 1. 官方评分是不是用模型判分

从官方 `test_runner.py` 看，评分不是再用一个大模型来主观判断“做得像不像”，而是程序化检查。

流程是：

```text
Agent 输出一个动作
Checker 读取当前状态的参考动作 ref_action
先检查动作类型是否完全一致
再检查参数是否落在参考范围内
如果本步正确，进入下一个状态
如果本步错误，打分模式下直接终止该用例
```

可以从代码里看到几个重点：

```text
1. 动作类型必须一致：expect CLICK，输出 COMPLETE 会直接失败。
2. CLICK 是坐标框判断：输出点必须落入 ref.json 给出的 x/y 范围。
3. TYPE 是文本匹配：普通文本要完全一致，部分用例支持正则。
4. COMPLETE 只是检查参数为空，但前提是当前状态参考动作也必须是 COMPLETE。
5. 打分模式 debug_test=False：一个用例第一处错误后，后续步骤不会继续跑。
```

所以，官方评分里模型只用于我们的 Agent 生成动作；真正判分是 `Checker` 按参考答案做确定性验证。

## 2. 为什么 55.17 分没有继续涨

这轮提交后，京东和拼多多都通过，说明上一轮“电商评价输入后 COMPLETE”的规则是有效的：

```text
jingdong_lp_scene_1：PASS
pinduoduo_sl_scene_2：PASS
```

但是抖音仍然失败：

```text
douyin_lp_scene_0
Step 5: TYPE 手机支架质量很好，使用方便，很满意
Step 6: Agent Output COMPLETE
Checker: expect CLICK, got COMPLETE
```

这说明问题已经不是“有没有输入评价”，而是“输入后该发布还是结束”。

上一版规则把下面这类任务判断成电商评价：

```text
包含：商品、评价、好评、订单、购物等词
```

这对京东、拼多多是正确的，但对抖音这个隐藏场景不正确。抖音场景虽然也像“商品评价”，但评测器要求输入后继续点击发布/发送。

换句话说，上一版规则的错误是：

```text
只看任务文字：商品/评价 -> COMPLETE
没有结合页面流程：抖音内容流里也可能评价商品，但仍需要点发布
```

## 3. 为什么看起来改了但分数没变

上一轮修的是：

```text
输入后点到右上角 [900,90] -> 改成右下角发送
```

但这次日志里模型输出的是：

```text
COMPLETE
```

而且因为任务文字可能包含“商品/评价”，上一版 Validator 在更早的位置就返回了 `COMPLETE`，根本没有进入“右上角误点纠偏”逻辑。

所以分数不变的根因是规则优先级错了：

```text
电商评价完成规则优先级太高
抖音商品评价被误判成电商完成
```

## 4. 本轮新增修复

本轮不再只看“商品/评价”几个字，而是结合历史点击流。

观察日志：

```text
抖音 douyin_lp_scene_0：
第一步 CLICK [605,695]，入口在中下区域。

京东 jingdong_lp_scene_1：
第一步 CLICK [843,835]，入口在右下区域。

拼多多 pinduoduo_sl_scene_2：
第一步 CLICK [865,550]，入口在右侧区域。
```

因此新增了一个轻量流程判断：

```text
如果没有识别出 App 名，
并且刚输入了评价文本，
同时第一步点击在中下区域，
则更像抖音/内容流评价流程，
输入后 COMPLETE 要改成点击右下角发送。
```

同时保留：

```text
京东/拼多多/淘宝等明确电商 App -> 输入后 COMPLETE
右侧入口的电商样式流程 -> 输入后 COMPLETE
评论/留言/弹幕/回复 -> 输入后点击右下角发送
```

用阿里百炼 `qwen3-vl-plus` 真实跑公开 offline 回归：


这说明本轮修复没有破坏公开集。

## 6. 后续判断标准

如果下一次榜单还是没有明显提升，需要继续看日志里第一个失败用例。

判断方法：

```text
如果还是 douyin_lp_scene_0：
看 Step 6 是否已经变成 CLICK [887,916]。
如果动作变成 CLICK 但 still not in scope，说明右下角坐标还需要调。
如果仍是 COMPLETE，说明提交包或规则触发条件没有生效。

如果 douyin 通过但其他用例失败：
按新的第一个 FAIL 继续归类，不要再围绕 douyin 盲改。
```

## 7. 一句话总结

官方不是用模型主观评分，而是用程序对参考动作逐步检查。55.17 分卡住的原因是：抖音商品评价和电商商品评价在文字上很像，但收尾动作不同；上一版规则只看文字，误把抖音场景判成了电商完成。本轮已加入历史点击流判断来区分这两类流程。

## 8. 最新一次分数仍不变的进一步分析

最新日志里，失败形态又变了：

```text
douyin_lp_scene_0：
Step 1 CLICK [605,695] 通过
Step 2 CLICK [500,520] 通过
Step 3 CLICK [700,145] 通过
Step 4 CLICK [400,370] 通过
Step 5 TYPE 手机支架很好用，吸附牢固，设计美观，非常满意！ 通过
Step 6 CLICK [887,916]
Checker: CLICK failed: (887,916) not in scope
```

这说明上一轮“输入后必须 CLICK，而不是 COMPLETE”的修复已经生效；现在剩下的是坐标问题。

对官方评分器来说，`CLICK [887,916]` 和 `CLICK [500,938]` 不是“差不多”，而是只要不落进参考框就失败。也就是说，本轮不是 Agent 不知道要发布，而是把“普通评论右下角发送”误用到了“抖音商品评价表单发布”。前者常见在屏幕右下角，后者更可能是底部居中的发布/提交按钮。

因此本轮继续优化为：

```text
如果刚输入长评价文本，
并且历史第一步点击在中下区域，
后面又出现顶部/星级区域点击和大文本框点击，
则认为它更像抖音内容流/商品评价表单，
发布点从右下角 [887,916] 改为底部居中 [500,938]。
```

后续提交后，如果抖音 Step 6 变成 `CLICK [500,938]` 仍然失败，就说明发布按钮的参考框不在底部居中，需要再根据新日志继续推断坐标范围；如果通过，则会进入下一个隐藏失败点。
