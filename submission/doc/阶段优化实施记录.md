# 阶段优化实施记录

## 2026-04-30：第一阶段和第二阶段落地

本轮按照 `现状分析及后续建议.md` 的规划，没有继续新增固定坐标补丁，而是先补两层基础能力。

第一层是可观测性。新增了 `utils/jsonl_logger.py`，本地调试时只要设置：

```powershell
$env:GUI_AGENT_JSONL_LOG="code-for-student/output_debug/decisions.jsonl"
```

Agent 每一步都会记录：

```text
当前 step
用户任务
task_slots
recent_actions
模型原始输出
Parser 解析结果
Validator 后的最终动作
Memory 当前阶段
异常信息
```

这个日志默认关闭，不影响正式提交。它的作用是：以后看到隐藏榜单失败，不需要只靠肉眼猜，可以先看模型原始判断和最终被 Validator 改成了什么。

第二层是失败日志分析工具。新增了：

```text
tools/analyze_failures.py
```

用法：

```powershell
python tools/analyze_failures.py code-for-student/output/test_run.log
```

它会把官方日志里的失败自动归类为：

```text
click_miss：动作是 CLICK，但坐标没落入官方范围
wrong_action：动作类型错
early_complete：官方要 CLICK，但 Agent 提前 COMPLETE
extra_click_after_done：官方要 COMPLETE，但 Agent 又 CLICK
type_mismatch：输入文本不匹配
```

第三层是评论/评价收尾状态机。新增了：

```text
utils/state_machine.py
```

原来 `validator.py` 里评论/评价逻辑是许多 if 分支混在一起，现在集中到 `ReviewFinishStateMachine`：

```text
普通评论：输入后点右下角发送 [887,916]
表单评价：输入后点底部居中发布 [500,938]
电商评价：京东/拼多多/淘宝输入评价后 COMPLETE
未知评价：保留旧兜底策略
```

这里特别针对 55.17 分卡点做了约束：只有历史动作同时满足“中下区域入口 + 顶部/星级区域点击 + 大文本框点击”时，才认为是表单评价，避免把普通评论误判成底部居中发布。

## 验证结果

本轮做了三类验证：

```text
1. py_compile：通过。
2. 评论/评价状态机单测：通过。
3. 无 API 本地回归：6/11。
```

无 API 回归 6/11 是预期内结果，因为无 API fallback 只覆盖了一部分公开流程，正式高分仍依赖 VLM。关键是本轮没有改动官方 API 调用方式，也没有把日志写入正式提交流程。

## 下一步

下一阶段建议开始做“候选元素层”，但不要一次性替换所有点击。先只在评论/评价收尾里使用候选元素：

```text
bottom_right_send
bottom_center_submit
top_right
bottom_input
middle_button
```

等这一层稳定后，再把搜索、地图、视频播放类动作逐步迁移到候选元素中心点。

## 2026-04-30：第三阶段候选元素层落地

本轮新增了轻量候选元素层，目标是逐步把“模型直接猜坐标”升级成“模型或规则选择元素，再由程序取元素中心点”。

新增文件：

```text
code-for-student/utils/ui_elements.py
code-for-student/utils/candidate_miner.py
```

`UIElement` 统一表示一个可点击候选区域：

```text
element_id
kind
bbox
center
hint
score
```

`CandidateMiner` 当前先生成启发式候选，不引入 OCR，避免工程复杂度过高。第一批候选包括：

```text
top_search：顶部搜索框
top_right：右上角搜索/完成
first_card：第一个结果卡片
middle_button：中部主按钮
bottom_input：底部输入框
bottom_right_send：右下发送
bottom_center_submit：底部居中提交
left_top_back：左上返回/关闭
```

为了保持兼容，`bottom_right_send` 的中心仍是 `[887,916]`，`bottom_center_submit` 的中心仍是 `[500,938]`。也就是说，本轮不是贸然改坐标，而是先把旧坐标包装成可解释元素。

接入点：

```text
Agent 每一步开始时生成候选元素。
Memory 保存 last_candidates。
JSONL 日志会记录候选元素列表。
ReviewFinishStateMachine 不再直接写死发送点，而是从候选元素里取 bottom_right_send / bottom_center_submit。
Validator 也支持 target_id / element_id，后续严格 JSON 输出可以直接选择候选元素。
```

验证结果：

```text
py_compile：通过
候选元素 + 评论/评价状态机单测：通过
无 API 本地回归：6/11，和上一阶段一致
```

这说明第三阶段已经完成“结构升级”，但还没有扩大到所有点击场景。下一步可以进入第四阶段：把 Prompt 改成严格 JSON，并要求模型优先输出 `target_id`。

## 2026-05-02：第四阶段 Prompt 结构化输出落地

本轮目标是让第三阶段的候选元素真正参与 VLM 决策。之前程序虽然已经生成了候选元素，但 Prompt 没有明确告诉模型“先选元素 id”，所以模型仍然容易直接猜裸坐标。第四阶段把 Prompt 改成了更明确的结构：

```text
当前可点击候选元素：
[{"id": 6, "kind": "bottom_right_send", "center": [887, 916], ...}]
```

并把点击输出改成优先使用：

```json
{"action":"CLICK","target_id":7}
```

只有候选元素明显没有目标控件时，才允许模型输出：

```json
{"action":"CLICK","point":[500,500]}
```

这一步的意义是：模型负责判断“该点哪个控件”，程序负责把控件 id 转成稳定中心点。这样可以减少 VLM 直接猜坐标导致的 `CLICK failed: not in scope`。

配套改动：

```text
PromptBuilder：把候选元素列表写入 Prompt，并要求 Action 行输出 JSON。
OutputParser：兼容 JSON、click(target_id=7)、Action: CLICK target_id=7 等写法。
Validator：当 target_id 和 point 同时出现时，优先使用 target_id 对应候选元素中心。
CandidateMiner：补充“提交”关键词，让评价/评论场景更稳定地提升底部候选元素优先级。
```

验证结果：

```text
py_compile：通过
target_id 解析测试：通过
target_id 优先级测试：通过，target_id=7 会覆盖错误 point=[1,2]，最终点击 [500,938]
Prompt 预览测试：通过，候选元素 JSON 列表已进入提示词
无 API 本地回归：6/11，和第三阶段一致
```

需要注意：无 API 回归不会体现这轮收益，因为它主要走规则和兜底，不会真实模拟 VLM 是否更愿意输出 `target_id`。第四阶段的真实价值要看官方/真实 VLM 评测日志里 `raw_output` 是否开始出现 `target_id`，以及 `CLICK failed: not in scope` 是否下降。
