## 2026-05-03：官方隐藏日志首步评价入口修复

用户提供的最新官方隐藏评测日志显示，分数降低的首要原因不是公开集回归失败，而是评价/晒单类隐藏用例在第 1 步误点：


本轮修复：

```text
- 新增 right_middle_review_entry 和 lower_middle_review_entry。
- 在 step=1、无历史动作、任务像评价/晒单/评论时，提升评价入口候选，降低 bottom_right_send、bottom_center_submit、left_top_back。

validator.py：
- 新增 _correct_initial_review_entry_point。
- 仅在首步评价上下文中，把已观察到的底部右侧误点纠到 [605,695]，把左上返回误点纠到 [865,550]。

prompt_builder.py：
- 新增规则：评价/晒单/评论任务第 1 步且未输入内容时，不要点击发送/发布/提交/返回。

state_machine.py：
- 新增右侧电商评价流识别，避免电商晒单后续被“发布”等词误导成社交发送。
```

本轮按照 `现状分析及后续建议.md` 的规划，没有继续新增固定坐标补丁，而是先补两层基础能力。

第一层是可观测性。新增了 `utils/jsonl_logger.py`，本地调试时只要设置：

第二层是失败日志分析工具。新增了：

第三层是评论/评价收尾状态机。新增了：

新增文件：

`UIElement` 统一表示一个可点击候选区域：

## 2026-05-02：第四阶段 Prompt 结构化输出落地

本轮目标是让第三阶段的候选元素真正参与 VLM 决策。之前程序虽然已经生成了候选元素，但 Prompt 没有明确告诉模型“先选元素 id”，所以模型仍然容易直接猜裸坐标。第四阶段把 Prompt 改成了更明确的结构：

```text
当前可点击候选元素：
[{"id": 6, "kind": "bottom_right_send", "center": [887, 916], ...}]
```

并把点击输出改成优先使用：

```json
{"action":"CLICK","target_id":7}
```

只有候选元素明显没有目标控件时，才允许模型输出：

```json
{"action":"CLICK","point":[500,500]}
```

这一步的意义是：模型负责判断“该点哪个控件”，程序负责把控件 id 转成稳定中心点。这样可以减少 VLM 直接猜坐标导致的 `CLICK failed: not in scope`。

配套改动：

```text
PromptBuilder：把候选元素列表写入 Prompt，并要求 Action 行输出 JSON。
OutputParser：兼容 JSON、click(target_id=7)、Action: CLICK target_id=7 等写法。
Validator：当 target_id 和 point 同时出现时，优先使用 target_id 对应候选元素中心。
CandidateMiner：补充“提交”关键词，让评价/评论场景更稳定地提升底部候选元素优先级。
```

验证结果：

```text
py_compile：通过
target_id 解析测试：通过
target_id 优先级测试：通过，target_id=7 会覆盖错误 point=[1,2]，最终点击 [500,938]
Prompt 预览测试：通过，候选元素 JSON 列表已进入提示词
无 API 本地回归：6/11，和第三阶段一致
```

需要注意：无 API 回归不会体现这轮收益，因为它主要走规则和兜底，不会真实模拟 VLM 是否更愿意输出 `target_id`。第四阶段的真实价值要看官方/真实 VLM 评测日志里 `raw_output` 是否开始出现 `target_id`，以及 `CLICK failed: not in scope` 是否下降。

## 2026-05-02：真实 VLM 日志闭环优化

这一轮专门用真实 VLM 日志检查两件事：

```text
1. 模型是否按 Prompt 输出 target_id。
2. 哪些场景仍然绕回裸坐标或选错候选元素。
```

结论很清楚：第四阶段 Prompt 是有效的，主要问题从“模型乱猜坐标”变成了“候选元素覆盖不够细”。因此后续优化没有继续堆 Prompt，而是根据真实失败日志补候选层。

分数变化：

```text
v1：7/11 = 63.64%
v2：8/11 = 72.73%
v3：9/11 = 81.82%
v4：10/11 = 90.91%
v5：10/11 = 90.91%，但芒果 TV 已修复，失败转移到百度地图开屏跳过
v6：11/11 = 100.00%
```

关键修改：

```text
CandidateMiner：
- 为爱奇艺、百度地图、芒果 TV、腾讯视频分别细化右上角跳过/关闭候选框。
- 为百度地图“导航语音包”补充“我的”入口和“语音包入口”候选。
- 为芒果 TV“我的下载”补充“我的 tab”“我的下载入口”“已下载剧集条目”候选。
- 为腾讯视频搜索补充“搜索建议/搜索提交”候选。

ActionValidator：
- 保留 target_id 优先级。
- 增加一个很窄的裸坐标纠偏：当百度地图前两步模型把顶部广告跳过误输出为裸点时，吸附回 top_right 候选。
```

最终真实 VLM 日志：

```text
总用例数：11
通过用例数：11
用例准确率：100.00%
VLM 决策记录：14
VLM 原始输出包含 target_id：13
VLM 原始输出包含 point：0
解析后动作类型：CLICK_TARGET_ID 13 次，TYPE 1 次
```

通俗理解：现在模型不再直接负责“猜屏幕坐标”，而是先从我们给它的候选元素里选编号。程序再把编号转成坐标。这样 VLM 做它擅长的语义判断，代码负责稳定落点，整体会比纯坐标输出可靠得多。
