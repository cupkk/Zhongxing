# 项目深度分析与后续任务规划（2026-05-03）

## 0. 一句话结论

当前项目已经从“让 VLM 直接猜坐标”升级为“候选元素 + target_id + Validator 校验”的高分路线。公开集和本地回归已经做到满分，但官方隐藏集分数下降说明问题已经进入第二阶段：不是主流程缺失，而是候选元素覆盖、任务阶段判断、隐藏变体回归和首错日志闭环还不够强。

下一阶段冲最高分的重点不是继续堆更长 Prompt，也不是盲目写更多固定坐标，而是把当前启发式方案升级成更稳的工程闭环：

```text
失败日志 -> 首错分类 -> 候选元素补强 -> 状态机/Validator 窄域修复 -> 公开回归 -> 重新打包
```

## 1. 赛题与评分要求分析

### 1.1 基本比赛要求

根据 `赛题.md`，本赛题要求实现一个手机 GUI Agent，根据用户自然语言指令和当前手机截图输出下一步动作。限制条件如下：

- 提交语言：Python。
- 推荐环境：Python 3.10.12。
- 最终提交：`submission.zip`。
- 解压后总大小不超过 20 MB。
- 必须包含 `src/agent.py`。
- `src/agent_base.py` 是主办方基类，不应修改。
- 坐标必须是 0 到 1000 的归一化坐标，不是截图真实像素。

合法动作只有五类：

```text
OPEN     {"app_name": "..."}
CLICK    {"point": [x, y]}
TYPE     {"text": "..."}
SCROLL   {"start_point": [x1, y1], "end_point": [x2, y2]}
COMPLETE {}
```

最终总分公式：

```text
总得分 = 打榜得分 * 60% + Agent代码 * 20% + 设计方案及创新 * 20%
```

这意味着只有线上 case 分数高还不够，文档中也要清楚解释架构、创新点、实验记录和失败闭环，否则代码分与设计分可能吃亏。

### 1.2 官方评测器的真实判分逻辑

`code-for-student/test_runner.py` 的关键逻辑是程序化判分，不是再让一个模型主观打分：

- `Checker.check()` 先比较动作类型，`CLICK`、`TYPE`、`COMPLETE` 等必须完全一致。
- `CLICK` 要求输出点落入 `ref.json` 给定的 x/y 范围。
- `TYPE` 普通文本必须完全一致，少数用例支持 `正则 ...`。
- `COMPLETE` 只有在当前参考动作也是 `COMPLETE` 时才有意义。
- `--no_debug_test` 也就是打分模式下，一个 case 第一处失败会立即终止后续执行。

这对策略有三个直接影响：

1. **首错最重要。** 后面步骤再正确也没有机会执行。
2. **点击接地比语义更硬。** 语义上“点发送”没用，点不进 ref 框就是 0。
3. **COMPLETE 风险极高。** 期望 `CLICK` 时输出 `COMPLETE` 会直接失败，反过来也会失败。

### 1.3 公开 ref 数据统计

本次重新统计 `code-for-student/test_data/offline/*/ref.json`：

```text
公开 case 数：11
名义步骤数：108
平均每个 case：9.82 步
最短 case：7 步
最长 case：15 步

动作分布：
OPEN: 11
CLICK: 72
TYPE: 14
COMPLETE: 11
```

CLICK 占绝对多数，所以分数主要由点击动作决定。公开集中还有 18 个状态存在多分支可接受动作，说明评测并非完全单路径，但每一步的允许范围仍然严格。

部分公开 CLICK 框很窄，例如：

```text
快手筛选按钮：x 宽约 42，y 高约 24
喜马拉雅搜索图标：x 宽约 54，y 高约 22
抖音底部入口：x 宽约 83，y 高约 32
```

这解释了为什么“模型大概点对区域”仍然不够，必须把目标控件接地到稳定中心点。

## 2. 当前项目架构分析

### 2.1 主流程

当前 `code-for-student/agent.py` 的主流程是：

```text
parse_task
-> CandidateMiner.build
-> RulePolicy.pre_decide
-> PromptBuilder.build
-> BaseAgent._call_api
-> OutputParser.parse
-> ActionValidator.validate
-> DecisionLogger.log
-> AgentMemory.update
```

这个结构是正确的，已经具备成熟 GUI Agent 的基本闭环：任务解析、候选生成、模型决策、输出解析、动作校验、历史记忆、日志记录。

### 2.2 当前优势

#### 优势一：target_id 接地路线正确

`CandidateMiner` 先生成候选元素，`PromptBuilder` 要求模型优先输出：

```json
{"action":"CLICK","target_id":7}
```

然后 `ActionValidator` 把 `target_id` 转成候选元素中心点。这是目前最重要的技术路线，因为它把任务拆成两件事：

```text
VLM：判断应该点哪个元素
本地代码：把元素编号转成稳定坐标
```

这比让模型直接输出 `[x, y]` 稳得多。

#### 优势二：输出解析和动作校验较完善

`OutputParser` 支持 JSON、比赛格式、函数式格式、中文动作描述等多种输出。`ActionValidator` 会做动作名标准化、坐标裁剪、TYPE 文本修正、COMPLETE 门槛判断、重复点击防护和评论/评价收尾修正。

这能降低模型输出格式波动对分数的影响。

#### 优势三：已经有日志闭环雏形

`DecisionLogger` 支持通过 `GUI_AGENT_JSONL_LOG` 打开 JSONL 决策日志，记录：

```text
step
instruction
task_slots
recent_actions
raw_output
parsed_decision
final_action
candidates
memory_stage
pending_after_type
```

这对隐藏榜失败分析很重要。下一阶段应把它进一步接到失败分析工具和伪隐藏评测里。

#### 优势四：公开集和无 API 保底已很强

当前文档和计划文件记录，公开无 API 回归已达 `11/11 = 100.00%`。这说明规则模板作为保底能稳定覆盖公开样例，也证明提交包结构和接口基本可用。

#### 优势五：最新隐藏日志修复方向正确

用户提供的官方日志显示：

```text
douyin_lp_scene_0 step 1: CLICK [887,916] not in scope
pinduoduo_sl_scene_2 step 1: CLICK [70,85] not in scope
```

当前修复选择了窄域方案：

- `candidate_miner.py` 增加首步评价入口候选。
- `validator.py` 只在首步评价上下文纠偏两个已观察风险区域。
- `prompt_builder.py` 明确首步评价任务不能点发送/发布/提交/返回。
- `state_machine.py` 区分右侧电商评价流。

这个方向比全局改坐标安全，因为它解释的是“失败机制”，不是单纯追一个坐标。

### 2.3 当前不足

#### 不足一：候选元素仍是启发式矩形，不是真正视觉检测

`CandidateMiner` 当前主要生成固定区域：

```text
top_search
top_right
first_card
middle_button
bottom_input
bottom_right_send
bottom_center_submit
left_top_back
bottom_right_tab
search_submit_or_suggestion
right_middle_review_entry
lower_middle_review_entry
```

这已经比裸坐标好，但隐藏集页面一旦按钮位置变化、弹窗样式变化、入口文字变化，候选中心仍可能偏离 ref 框。缺少 OCR、图标检测、按钮轮廓检测或 Set-of-Mark 标注，是当前最大泛化短板。

#### 不足二：`RulePolicy` 模板收益高，但隐藏过拟合风险也高

`policy.py` 对美团、抖音、快手、哔哩哔哩、去哪儿、腾讯视频、芒果TV、喜马拉雅、爱奇艺、百度地图等公开流程写了大量 step 级模板。

好处是公开集和无 API 模式稳定。

风险是隐藏集只要同 App 页面状态不同，固定 step 和固定坐标会抢在 VLM 之前输出错误动作。后续应把模板分层：

```text
P0 强规则：OPEN、明确重复点击恢复、无 API fallback
P1 中规则：明确公开流程保底，仅在 no_api 或高置信条件下触发
P2 弱规则：转为 candidate boost 或 prompt hint，不直接输出动作
```

#### 不足三：Memory 阶段状态还偏薄

`AgentMemory` 当前记录了动作、已打开 App、已输入文本、pending_after_type、last_candidates 等。它能支撑基本防循环和评论收尾，但还不能精细表达：

```text
当前处于 search_submit / address_confirm / review_entry / review_form / comment_send / popup_close / result_open 哪个阶段
哪些候选元素已经尝试过
是否刚从弹窗恢复
是否进入了表单评价页而不是普通评论区
```

因此 Validator 仍需要靠历史点位和 App 名去推断流程。

#### 不足四：评论/评价状态机是正确方向，但还不够可测试

`ReviewFinishStateMachine` 已经区分：

```text
form_review_flow
right_side_ecommerce_flow
ecommerce apps
social apps
explicit publish words
```

但目前缺少独立单测覆盖不同历史点击流：

- 抖音表单评价：应点 bottom_center_submit。
- 爱奇艺普通评论：应点 bottom_right_send。
- 京东/拼多多右侧入口评价：应 COMPLETE。
- 未知 App 输入长评价：不应过早全局修正。

隐藏集最新失败正发生在评价/晒单场景，这块必须补测试。

#### 不足五：缺少伪隐藏集

公开 11/11 不能证明隐藏集稳定。当前项目没有系统生成 30 条左右伪隐藏用例，也没有对任务表达、App、入口、按钮位置、收尾动作做扰动测试。

这会导致优化过度依赖用户提供的官方失败日志，迭代速度慢。

#### 不足六：文档与提交目录有历史杂质

当前工作区存在评测输出、pycache 跟踪变化、submission 目录清理变化。虽然 zip 已检查干净，但仓库层面仍应在最终提交前做一次：

```text
源码同步检查
zip 内容检查
secret 扫描
doc/doc 重复检查
pycache 排除检查
```

## 3. 前沿文献与应用分析

本节只采用论文/项目主页等一手资料做对照。

### 3.1 AndroidWorld：评测必须动态化

AndroidWorld 提供真实 Android 环境、20 个真实 App、116 个程序化任务，并强调自然语言表达和任务参数可以动态变化。它的结论对本项目非常直接：固定公开样例得分并不能代表真实泛化，任务表达和状态扰动会显著影响 Agent 表现。

对本项目的启发：

- 必须自建伪隐藏集。
- 必须统计首错，而不是只看最终分数。
- 必须把任务类型抽象出来，不要只背公开 step。

来源：https://arxiv.org/abs/2405.14573

### 3.2 SeeClick：GUI grounding 是核心瓶颈

SeeClick 明确指出视觉 GUI Agent 的关键挑战是 GUI grounding，也就是根据指令准确定位屏幕元素。它只依赖截图，不依赖 HTML/XML，和本赛题截图输入条件接近。

对本项目的启发：

- “知道要点发送”不等于“点进官方 ref 框”。
- target_id 候选接地是正确路线。
- 下一阶段应提高候选质量，而不是继续要求 VLM 猜裸点。

来源：https://arxiv.org/abs/2401.10935

### 3.3 Mobile-Agent：视觉感知工具 + 任务分解

Mobile-Agent 先用视觉感知工具定位文字和图标，再基于视觉上下文做任务规划和逐步操作，并且不依赖 XML 元数据。

对本项目的启发：

- 当前 `CandidateMiner` 是 Mobile-Agent 感知层的轻量版本。
- 后续可以加入低成本视觉工具，例如按钮轮廓检测、OCR 候选、底部导航识别。
- 长任务不能只靠 step_count，应显式记录任务阶段。

来源：https://arxiv.org/abs/2401.16158

### 3.4 AppAgent：App 经验库不应等同于固定坐标

AppAgent 通过自主探索或人类演示形成 App 操作知识库，动作空间简化为点击、滑动等手机操作。

对本项目的启发：

- 可以保留 App profile，但 profile 应描述“页面阶段 + 目标控件语义”，不要只写死 step 坐标。
- 例如“抖音评论发布阶段优先寻找发送/发布按钮”，比“抖音第 6 步点 [887,916]”更稳。

来源：https://arxiv.org/abs/2312.13771

### 3.5 OS-Atlas：大规模 GUI 元素数据提升 OOD grounding

OS-Atlas 强调跨平台 GUI grounding 数据和 action model 对 OOD 泛化的重要性，并构建了大规模 GUI 元素语料。

对本项目的启发：

- 我们不能在比赛里训练大模型，但可以用工程方法模拟：更丰富候选元素、更稳定 target_id、更好的日志驱动修复。
- 隐藏集本质是 OOD 变化，应减少对公开坐标模板的依赖。

来源：https://arxiv.org/abs/2410.23218

### 3.6 UI-TARS：统一动作建模 + System-2 推理 + 反思轨迹

UI-TARS 是截图输入的原生 GUI Agent，强调统一动作空间、GUI 轨迹训练、反思和多步推理，在 AndroidWorld 等 benchmark 上报告了明显优于通用 VLM 的表现。

对本项目的启发：

- 本赛题动作空间已经统一，代码应把所有模型输出收敛到内部标准动作。
- 可以轻量模拟反思：对高风险 COMPLETE、首步评价、TYPE 后收尾做二次校验。
- 每次失败日志都是反思数据，应写入经验库或回归用例。

来源：https://arxiv.org/abs/2501.12326

### 3.7 ShowUI：视觉 token 和动作历史要结合

ShowUI 将视觉、语言、动作统一建模，并强调多轮 query-action 历史对 GUI 导航有效。

对本项目的启发：

- Prompt 中的候选元素和历史动作是必要信息。
- 但历史不能只给自然语言列表，还应在 Memory 中结构化为阶段状态。

来源：https://arxiv.org/abs/2411.17465

### 3.8 ScreenSpot-Pro：缩小搜索区域比全屏猜点更稳

ScreenSpot-Pro 和 ScreenSeekeR 的一个重要发现是，复杂 GUI grounding 中缩小搜索区域可以显著提升准确率。

对本项目的启发：

- 当前 target_id 候选列表就是“缩小搜索区域”的实现。
- 后续不要给模型全屏自由点，应该给少量高质量候选。
- 候选排序和候选召回同样重要。

来源：https://arxiv.org/abs/2504.07981

### 3.9 V-Droid / verifier-driven 思路：候选动作先评估再执行

V-Droid 使用 verifier 思路评估候选动作，而不是让生成器直接给最终动作。

对本项目的启发：

- 可以新增轻量 `ActionReranker`：把模型动作、规则动作、状态机动作和恢复动作统一打分。
- 对高风险状态，例如 TYPE 后、首步评价、弹窗关闭、COMPLETE，先生成 2-3 个候选动作再选择。

来源：https://arxiv.org/abs/2503.15937

## 4. 最高分路线规划

### P0：立即执行，保护当前基线

#### P0-1 建立官方日志首错分析 SOP

每次官方分数低于预期，必须先拿日志，不先改代码。记录：

```text
case_id
step
instruction
Agent action
ref action
失败原因：click_miss / wrong_action / type_mismatch / early_complete / late_click
raw_output 是否包含 target_id
final point 是否来自 candidate
```

产物：

- 扩展 `tools/analyze_failures.py`。
- 形成 `doc/失败日志分析模板.md` 或写入 journal。

#### P0-2 锁定 submission hygiene

每次提交前固定执行：

```powershell
python -m py_compile code-for-student/agent.py code-for-student/utils/*.py
python test_runner.py --output_dir ./output_noapi_final --no_debug_test
```

并检查：

```text
submission/src 与 code-for-student 同步
submission.zip 包含 src/agent.py
不含 __pycache__
不含 .pyc/.pyo
不含 doc/doc
不含真实密钥
```

#### P0-3 给评价/晒单首步和收尾补单测

当前最新隐藏失败都在评价/晒单任务，必须把这类规则变成可测试资产。

建议新增 `tools/test_review_state_machine.py` 或简单脚本，覆盖：

- 首步底部发送误点应纠到评价入口。
- 首步左上返回误点应纠到右侧评价入口。
- 表单评价输入后应点底部居中。
- 社交评论输入后应点右下发送。
- 京东/拼多多评价输入后应 COMPLETE。

### P1：提高隐藏泛化

#### P1-1 候选元素质量升级

在不引入重依赖的前提下增强 `CandidateMiner`：

- 根据当前截图尺寸和颜色/边缘找按钮轮廓。
- 识别底部导航栏 4-5 个等分 tab。
- 对顶部搜索框、右上跳过、底部输入框做更细 App/context 适配。
- 为弹窗生成 `popup_close`、`popup_allow`、`popup_cancel` 候选。
- 对候选加入 `source` 字段：`heuristic`、`app_profile`、`history_context`、`visual_scan`。

#### P1-2 Memory 阶段状态升级

建议 `AgentMemory` 增加：

```text
stage_history
clicked_element_ids
last_decision_source
last_parse_mode
pending_after_type = search_submit / review_finish / address_confirm / generic_submit
last_screen_state
```

目标是让 Validator 不再只靠 App 名和坐标猜流程。

#### P1-3 将固定模板降级为可控保底

当前 `_template_decide()` 直接接管大量 App 流程。建议拆成：

```text
RulePolicy.pre_decide_strong：只管 OPEN、重复点击恢复、高置信弹窗
RulePolicy.template_fallback：无 API 和公开回归保底
RulePolicy.bias_candidates：给 CandidateMiner 加权，不直接输出动作
```

隐藏集提交前是否启用全部模板，需要根据官方日志判断。如果模板明显导致隐藏首错，就要降级。

#### P1-4 ActionReranker

新增轻量候选动作排序层：

```text
model_candidate
target_id_candidate
review_state_candidate
recovery_candidate
fallback_candidate
```

打分依据：

- 是否来自 target_id。
- 是否符合 pending_after_type。
- 是否重复点击。
- 是否过早 COMPLETE。
- 是否符合任务类型。
- 是否属于首步评价禁点区域。

### P2：构造伪隐藏集

公开集只有 11 个 case，不能支撑最高分优化。建议构造至少 30 条伪隐藏测试：

```text
10 条评论/评价/晒单：
  抖音、快手、爱奇艺、京东、拼多多、未知 App
  覆盖右下发送、底部居中提交、输入后 COMPLETE

5 条搜索/播放：
  搜索框在顶部、中部、弹窗后
  搜索后点建议词或搜索按钮

5 条地图/出行：
  起点/终点顺序变化
  地址候选选择第一个
  语音包/导航/打车不同子流程

5 条弹窗：

```

## 5. 不建议继续做的事

### 5.1 不建议盲目扩大 Validator 坐标纠偏

例如把所有底部右侧点击都吸附到底部居中，短期可能修一个 case，但会破坏普通评论发送。

正确做法是：

```text

```

### 5.2 不建议继续让 Prompt 变得更长

当前 Prompt 已经包含大量规则。继续堆规则会增加注意力分散风险。更有效的是：

- 给更少但更准的候选元素。
- 让模型输出 target_id。
- 本地状态机处理高风险动作。

### 5.3 不建议在没有新官方日志时大改模板

当前公开和 no-api 已经满分，盲目重构模板可能造成回退。下一次代码改动应优先围绕：

```text
单测资产
候选元素增强
日志分析工具
文档同步
```
