# 冲分执行路线图（2026-05-03）

## 0. 当前判断

当前项目不是从零起步，而是已经进入“公开集满分后冲隐藏榜”的阶段。已有主线 `CandidateMiner + target_id grounding + ActionValidator + 状态机 + JSONL 日志` 是正确方向，本阶段不能推倒重来。

最重要的结论：

```text
要冲分，优先做隐藏首错闭环、候选覆盖率、动作验证和伪隐藏测试。
不要把主要精力继续放在更长 Prompt、更多裸坐标补丁或重写 RulePolicy。
```

当前可量化状态：

```text
公开 no-api 回归：11/11 = 100.00%
30 条伪隐藏机制测试：通过
公开 CLICK 候选中心覆盖率：44/79 = 55.70%
最新官方隐藏日志首错：评价/晒单首步入口误点
核心提交物：submission.zip
```

## 1. 评分要求对冲分的真实含义

赛题总分由三部分组成：

```text
总得分 = 打榜得分 * 60% + Agent代码 * 20% + 设计方案及创新 * 20%
```

因此后续任务要同时服务三件事：

1. **打榜得分**：减少隐藏 case 首错，尤其是 `CLICK not in scope`、提前 `COMPLETE`、TYPE 后收尾错误。
2. **代码分**：让架构清晰、可维护、可测试，而不是堆一堆无法解释的坐标 if。
3. **创新分**：把 target_id grounding、候选覆盖统计、伪隐藏机制测试、日志首错闭环写成完整方法论。

打榜阶段的评测逻辑很硬：动作类型必须匹配，`CLICK` 必须落入官方 ref 框，`TYPE` 多数要完全一致，`COMPLETE` 不能提前。一条 case 首错后就没有后续机会，所以冲分应以“首错清零”为中心。

## 2. 前沿方法给本项目的可落地启发

### 2.1 AndroidWorld：隐藏榜本质是动态任务变体

AndroidWorld 提供 20 个真实 Android App、116 个程序化任务，并强调任务可以参数化、自然语言表达可以变化，静态测试集并不能代表真实泛化能力。

对本项目的落地：

- 把 `tools/pseudo_hidden_checks.py` 从 30 条机制测试扩展到 80-120 条参数化测试。
- 任务模板要扰动 App 名、评论文字、搜索词、入口描述、弹窗类型、收尾词。
- 每次修改必须跑公开集和伪隐藏集，不能只看公开 11/11。

参考：[AndroidWorld](https://arxiv.org/abs/2405.14573)

### 2.2 SeeClick / OS-Atlas：GUI grounding 是主瓶颈

SeeClick 直接指出视觉 GUI Agent 的关键挑战是 GUI grounding，即根据任务准确定位屏幕元素。OS-Atlas 进一步说明 OOD 场景下 GUI grounding 数据和动作模型会显著影响泛化。

对本项目的落地：

- 继续坚持 target_id，不让模型直接猜裸坐标。
- `CandidateMiner` 下一阶段目标不是“更多固定点”，而是“更多可解释候选族”：列表行、右侧小按钮、顶部操作按钮、弹窗按钮、输入框、底部 tab、评价入口。
- 用候选覆盖率作为候选层的第一指标。当前 55.70%，下一目标 70%，冲刺目标 80%。

参考：[SeeClick](https://arxiv.org/abs/2401.10935)、[OS-Atlas](https://arxiv.org/abs/2410.23218)

### 2.3 ScreenSpot-Pro / ScreenSeekeR：缩小搜索区域比全屏猜点更稳

ScreenSpot-Pro 显示复杂 GUI 中目标尺寸小、页面复杂时，直接全屏定位表现很差；ScreenSeekeR 的关键思路是用规划器缩小搜索区域，再做级联搜索。

对本项目的落地：

- 把候选分成“全局通用候选”和“阶段候选”，不要每一步都把所有 25 个候选等权给模型。
- 根据任务阶段筛选 top-k 候选：搜索提交阶段只突出 `top_right/search_submit/keyboard_search`；评价首步只突出评价入口；TYPE 后只突出发送/提交/完成。
- Prompt 中候选排序要服务阶段，不只是固定顺序。

参考：[ScreenSpot-Pro](https://arxiv.org/abs/2504.07981)

### 2.4 V-Droid / VeriSafe Agent：用验证器选动作，不让生成器一票决定

V-Droid 的核心不是让 LLM 直接生成最终动作，而是先构造离散动作空间，再用 verifier 评估候选动作；它在 AndroidWorld、AndroidLab、MobileAgentBench 上报告了更好的成功率。VeriSafe Agent 则从逻辑验证角度证明，动作执行前的约束检查能明显减少错误。

对本项目的落地：

- 新增轻量 `ActionReranker` 或 `ActionVerifier`，输入为模型动作、候选动作、任务阶段和历史，输出最终动作。
- 第一版不调用额外 VLM，只做确定性打分：动作类型匹配阶段、是否过早 COMPLETE、是否点到了禁区、是否重复点击、是否刚 TYPE 后未收尾。
- 重点覆盖高风险状态：首步评价、TYPE 后收尾、弹窗、搜索提交、提前 COMPLETE。

参考：[V-Droid](https://arxiv.org/abs/2503.15937)、[VeriSafe Agent](https://arxiv.org/abs/2503.18492)

### 2.5 UI-TARS / ShowUI：统一动作空间、历史轨迹和反思校验

UI-TARS 强调 screenshot-native GUI Agent、统一动作空间和多步推理；ShowUI 强调视觉、语言、动作历史的统一建模。

对本项目的落地：

- 继续把所有输出收敛为官方五类动作：`OPEN / CLICK / TYPE / SCROLL / COMPLETE`。
- `Memory` 不只保存动作列表，还要保存阶段：`opened_app`、`search_input`、`search_submit`、`result_open`、`review_entry`、`review_form`、`comment_send`、`popup_recovery`、`done_ready`。
- Prompt 中给模型的历史应从“自然语言流水账”升级为“阶段摘要 + 最近动作 + 当前候选”。

参考：[UI-TARS](https://arxiv.org/abs/2501.12326)、[ShowUI](https://arxiv.org/abs/2411.17465)

### 2.6 Mobile-Agent / AppAgent：App 经验库应描述阶段语义，不应只写死坐标

Mobile-Agent 和 AppAgent 的共同经验是：移动端 Agent 需要任务分解、视觉感知和 App 操作知识。但 App 知识如果只变成固定坐标，会过拟合。

对本项目的落地：

- 建立 `app_profiles.py` 或在现有 `app_map/policy` 中分层表达 App 经验。
- Profile 只写“阶段 + 语义候选 + 禁止动作”，例如“评价首步应找订单/评价入口，不能点发送/提交/返回”。
- 只有公开集保底和官方隐藏首错修复，才允许窄域坐标纠偏。

参考：[Mobile-Agent](https://arxiv.org/abs/2401.16158)、[AppAgent](https://arxiv.org/abs/2312.13771)

## 3. 后续任务优先级

### P1：候选覆盖率从 55.70% 提到 70%+

目标：降低 VLM 裸点和 target_id 选错风险。

优先补的候选族：

```text
1. 列表行候选：list_row_1/list_row_2/list_row_3/list_row_4
2. 右侧小按钮候选：right_icon_top/right_icon_mid/right_icon_low
3. 顶部细粒度按钮：top_left_close/top_center_search/top_right_action
4. 地图/地址候选：address_result_1/address_result_2/route_confirm
5. 搜索结果候选：suggestion_row_1/result_card_1/result_card_2
6. 评价入口候选：review_entry_upper/right/middle/lower
```

注意：

- 候选是给模型选的，不等于强制点击。
- 不要为了覆盖公开 ref 直接把所有公开点写成 candidate。
- 新候选要有 `kind`、`hint`、阶段 boost/penalize，并进入覆盖统计。

验收：

```text
公开 CLICK 候选覆盖率 >= 70%
公开 no-api 仍为 11/11
30 条伪隐藏仍全通过
target_id 输出路径不退化
```

### P1：实现轻量 ActionVerifier / ActionReranker

目标：把 V-Droid 的 verifier-driven 思想落到本项目，不增加复杂模型依赖。

建议文件：

```text
code-for-student/utils/action_reranker.py
submission/src/utils/action_reranker.py
tools/test_action_reranker.py
```

第一版规则：

```text
首步评价/晒单：
  禁止 bottom_right_send、bottom_center_submit、left_top_back
  提升 review_entry/list_row/right_icon

TYPE 后 review_finish：
  社交评论 -> bottom_right_send
  表单评价 -> bottom_center_submit
  电商订单评价 -> COMPLETE

搜索输入后：
  提升 keyboard_search_button、top_right_text_button、search_submit_or_suggestion
  禁止提前 COMPLETE

弹窗阶段：
  提升 popup_close_top_right、popup_cancel_bottom、popup_allow_bottom
  禁止点列表内容

提前 COMPLETE：
  未达到 min_actions、刚 OPEN、刚 TYPE、未输入必要 query 时禁止
```

验收：


### P2：伪隐藏测试扩展到 80-120 条

验收：

## 4. 不建议做的事

```text
不要重写主架构。
不要为了单个公开 ref 写全局坐标 if。
不要让 RulePolicy 抢走未知隐藏流程的所有决策权。
不要继续无限加长 Prompt。
不要在没有新官方日志时大改 Validator。

```

## 5. 推荐执行顺序

### 第 1 天：保分与候选覆盖

```text
1. 新增提交前检查脚本或 Make-like PowerShell 命令清单。
2. 扩展 CandidateMiner：列表行、右侧小按钮、地址结果、搜索结果候选。
3. 跑候选覆盖统计，目标从 55.70% 提到 70%。
4. 跑公开 no-api 和 30 条伪隐藏。
```

### 第 2 天：ActionVerifier / 阶段状态机

```text
1. 新增 action_reranker.py。
2. 补 15-25 条高风险动作验证单测。
3. Memory 增加 stage_before/stage_after。
4. PromptBuilder 用阶段摘要替代部分冗余说明。
```

### 第 3 天：伪隐藏扩展与文档冲刺

```text
1. pseudo_hidden_checks.py 扩展到 80+。
2. analyze_failures.py 输出 failure_summary.md 和 suggested_layer。
3. 更新算法设计说明文档，把 verifier、coverage、state machine 写成创新点。
4. 同步 submission/src 和 submission/doc，重新打包验包。
```

### 有新官方日志时：立即插队

```text
1. 先运行 analyze_failures.py。
2. 只看每个失败 case 的首错。
3. 判断修复层：候选缺失、状态机、Validator、RulePolicy、Prompt、解析器。
4. 最小改动修复。
5. 跑公开集 + 伪隐藏 + zip 检查。
```

## 6. 下一步最值得马上做的三件事

1. **CandidateMiner 覆盖提升**：围绕 coverage report 的低覆盖 case，补通用候选族，把覆盖率拉到 70%。
2. **ActionReranker**：把首步评价、TYPE 后收尾、搜索提交、弹窗、提前 COMPLETE 统一进一个验证层。
3. **伪隐藏扩展**：从 30 条扩到 80+，让每次代码改动有更接近隐藏榜的回归压力。
