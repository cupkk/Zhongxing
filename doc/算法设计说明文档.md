# 基于候选元素 target_id 接地与状态机校验的移动端 GUI Agent

## 1. 赛题理解

本赛题要求 Agent 根据用户指令和当前手机截图，逐步输出标准动作并完成手机 App 任务。官方评测器会按 `ref.json` 逐步检查动作：

```text
OPEN / CLICK / TYPE / SCROLL / COMPLETE
```

整条任务执行到完成状态才计 1 分，中途任一步失败则该 case 计 0 分。`CLICK` 坐标必须落入官方给定的归一化坐标范围，`TYPE` 文本必须匹配，`COMPLETE` 只能在参考动作也是完成时通过。

因此，本方案的核心目标不是让模型自由输出坐标，而是让模型做它擅长的语义判断，再由本地代码完成稳定接地、格式转换和高风险动作校验。

## 2. 总体架构

核心代码位于 `src/agent.py` 和 `src/utils/`：

```text
agent.py                 Agent 主流程
utils/task_parser.py     任务槽位抽取
utils/candidate_miner.py 候选 UI 元素生成
utils/ui_elements.py     候选元素数据结构
utils/prompt_builder.py  带候选元素的 VLM Prompt
utils/output_parser.py   模型输出容错解析
utils/validator.py       标准动作校验与修正
utils/state_machine.py   评论/评价高风险流程状态机
utils/memory.py          历史动作和阶段记忆
utils/policy.py          高置信规则与无 API 兜底
utils/jsonl_logger.py    本地 JSONL 决策日志
```

主流程为：

```text
TaskParser
-> CandidateMiner
-> RulePolicy
-> PromptBuilder
-> VLM
-> OutputParser
-> ActionValidator
-> ReviewFinishStateMachine
-> AgentOutput
-> Memory + JSONL Log
```

## 3. 候选元素 + target_id 接地

早期方案容易让 VLM 直接输出裸坐标，例如：

```json
{"action":"CLICK","point":[887,916]}
```

这种方式在语义上可能正确，但只要坐标没有落入官方 ref 框，仍会失败。当前方案改为：

```json
{"action":"CLICK","target_id":7}
```

执行过程是：

1. `CandidateMiner` 根据任务、App、步骤和历史动作生成候选元素。
2. `PromptBuilder` 把候选列表写入 Prompt。
3. VLM 优先选择 `target_id`。
4. `ActionValidator` 根据 `target_id` 找到候选元素中心点，再输出官方 `CLICK {"point":[x,y]}`。

候选元素示例：

```text
top_search
top_right
first_card
bottom_input
bottom_right_send
bottom_center_submit
left_top_back
bottom_right_tab
search_submit_or_suggestion
popup_close_top_right
popup_cancel_bottom
popup_allow_bottom
right_middle_review_entry
lower_middle_review_entry
keyboard_search_button
```

这样把“应该点哪个控件”和“最终点哪个坐标”分开，降低裸坐标漂移风险。

## 4. 任务槽位解析

`task_parser.py` 从用户指令中抽取 App、搜索词、评论文本、店铺、商品、起点、终点等槽位。

典型用途：

- 视频/音频任务：提取剧名、歌名、搜索词。
- 地图任务：提取起点、终点、语音包人物名。
- 外卖/购物任务：提取店铺名和商品名。
- 评论/评价任务：提取要输入的评论或评价内容。

当模型输出泛化文本，例如“搜索内容”或“请输入评论”时，`ActionValidator` 会用任务槽位替换成真实文本。

## 5. 输出解析与标准化

`OutputParser` 兼容多种模型输出格式：

```text
JSON
Action: {"action":"CLICK","target_id":7}
CLICK:[[x, y]]
click(target_id=7)
type(text="...")
中文动作描述
```

解析后统一交给 `ActionValidator`。Validator 负责：

- 统一动作名，如 `tap`、`press`、`点击` -> `CLICK`。
- 修正参数 key，如 `content` -> `text`。
- target_id 优先于裸 point。
- 坐标裁剪到 `[0, 1000]`。
- 防止连续重复点击。
- 拦截过早 `COMPLETE`。
- 对高风险评论/评价流程做状态机校验。

## 6. 评论/评价状态机

隐藏榜低分主要暴露在评论、评价、晒单流程。此类任务的难点是：输入文本后，有的场景需要点击发送，有的场景需要点击底部提交，有的电商评价输入后即可完成。

当前 `ReviewFinishStateMachine` 将收尾分为三类：

```text
普通社交/视频评论：输入后点击右下角发送。
表单评价：输入后点击底部居中提交/发布。
电商订单评价：京东、拼多多、淘宝等输入后可 COMPLETE。
```

同时根据历史点击流识别页面形态：

- 首步在中下区域、后续有星级/顶部选项、大文本框点击 -> 更像表单评价。
- 首步在右侧订单入口 -> 更像电商评价。
- App 属于视频/社交类或任务明确要求发布评论 -> 输入后必须发送。

针对官方隐藏日志中出现的首步误点，Validator 只在窄域条件下纠偏：

```text
评价/晒单/评论任务
step=1
无历史动作
底部右侧误点 -> 评价入口候选
左上返回误点 -> 右侧评价入口候选
```

该修复避免全局坐标重写，降低对已通过流程的影响。

## 7. RulePolicy 与 VLM 的分工

`RulePolicy` 保留高置信流程和无 API 兜底，主要用于：

- 第一步直接 `OPEN` 目标 App。
- 已知公开流程的稳定保底。
- 无 API 环境下保证本地回归可运行。
- 重复点击时转为滚动，避免死循环。

对未知隐藏页面，仍交给 VLM 结合截图和候选元素判断，避免完全依赖固定坐标模板。

## 9. 本地验证结果

当前本地验证包括：

```text
py_compile：通过
评价/晒单状态机单测：通过
30 条伪隐藏机制测试：通过
公开 no-api 打分模式：11/11 = 100.00%
```

候选覆盖统计显示，公开 ref 中名义 CLICK 步骤为 79 个，当前启发式候选中心覆盖 44 个，覆盖率为 55.70%。这说明候选层已经能覆盖大量通用动作，但仍有继续增强空间，后续可加入更细的视觉扫描、OCR 或 App profile。

## 10. 创新点总结

1. **target_id grounding**  
   VLM 选择候选元素编号，本地代码负责转坐标，降低裸坐标不稳定。

2. **候选元素动作空间压缩**  
   将全屏点击问题缩小为少量高价值候选，提升模型选择稳定性。

3. **状态机处理高风险收尾**  
   对评论、评价、晒单等隐藏集高频失败场景做流程级校验。

4. **日志驱动优化闭环**  
   通过 JSONL 日志、失败首错分析和候选覆盖统计定位问题，不盲目改 Prompt。

5. **轻量可提交实现**  
   不依赖大型本地 OCR 或训练模型，适配 20 MB 提交限制，并通过官方 `BaseAgent._call_api()` 调用统一 VLM。

## 12. 后续优化计划

下一阶段继续提升隐藏集分数：

1. 增强候选召回，尤其是地图、旅行、外卖等长流程中部按钮和列表项。
2. 将固定公开模板逐步拆成强规则、fallback 和 candidate bias。
3. 扩展 Memory 阶段，例如 `search_submit`、`address_confirm`、`review_finish`。
4. 加入轻量 ActionReranker，对模型动作、状态机动作和恢复动作统一排序。
5. 持续构造伪隐藏机制测试，避免只对公开样例和单条官方日志过拟合。
